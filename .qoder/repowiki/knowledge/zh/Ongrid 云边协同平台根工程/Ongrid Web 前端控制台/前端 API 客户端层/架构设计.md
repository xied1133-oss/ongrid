模块以 `client.ts` 中的 `request<T>` 函数为核心统一入口，所有业务 API 文件（如 `agents.ts`、`auth.ts`、`logs.ts`、`prometheus.ts` 等）均通过导入该函数发起请求，形成单向依赖：业务模块 → client → store/i18n。
- `client.ts` 负责：统一 BASE URL (`/api/v1`)、注入 `Authorization` Bearer Token、设置 `Accept-Language`、JSON/FormBody 序列化、非 JSON 响应文本回退、`ApiError` 异常抛出、401 时调用 `/auth/refresh` 刷新 access token 并去重重试、刷新失败触发 `useAuth.getState().logout()` 强制登出。
- 每个业务文件按领域划分（agents、alerts、audit、auth、chat、devices、edges、flows、grafana、imbridge、integrations、knowledge、kubernetes、logs、marketplace、mcp、monitorPanels、operations、operatorRuns、orgs、packetCaptures、pages、prom、prometheus、reports、secrets、settings、skills、systemHealth、systemUpgrade、tasks、topology、traces、users、version、webshell），仅暴露类型定义与 `request` 调用包装的函数，不持有状态。
- 类型定义与后端 DTO 一一对应（注释中常标注 `mirrors backend ...`），保证前后端契约一致。
- 测试文件（`*.test.ts`）与业务文件并列放置，覆盖 logs、operations、skills 等关键模块。
